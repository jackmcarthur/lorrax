# Quickstart

This runs one complete static-COHSEX calculation end-to-end on a fresh clone — the bundled
regression fixture — with **no GPU and no native (FFI) build**. It is the one command
guaranteed to exist and succeed, and the fastest way to confirm LORRAX works on your
machine.

If you have a crystal rather than a fixture, the step *before* this one — getting a
`WFN.h5` out of a DFT code — is [Preparing inputs from DFT](preprocessing.md).

## 1. Install (pure-JAX, CPU)

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh    # one-time
git clone <lorrax-repo-url> && cd lorrax
uv sync                                            # editable install; puts src/ on sys.path
```

## 2. Run the bundled fixture

```bash
uv run python -m gw.gw_jax -i tests/regression/cohsex_debug/cohsex_test.in
# console-script equivalent:
uv run gw_jax -i tests/regression/cohsex_debug/cohsex_test.in
```

On Perlmutter, run it on a compute node instead — never on a login node:

```bash
cd tests/regression/cohsex_debug
lx run python3 -u -m gw.gw_jax -i cohsex_test.in
```

The fixture ships its own wavefunction
(`WFNsmall.h5`), centroids (`centroids_frac_60.txt`), `dipole.h5`, and `kin_ion.h5`, so it
needs nothing native. It writes `eqp_test.dat`; the reference is `eqp_ref.dat` in the same
directory.

## 3. Check the answer

The fixture does not check itself. Compare:

```bash
cd tests/regression/cohsex_debug
diff <(sed 1d eqp_test.dat) <(sed 1d eqp_ref.dat)
```

`sed 1d` drops the `# Generated by LORRAX … UTC` timestamp, which always differs.

**Tolerance: agreement to ~1e-6 eV absolute is a pass.** Measured 2026-08-06 (see the
banner at the foot of this page), the command above prints **four lines**, all of them the
last digit of a `VH` value on a ~200 eV quantity:

```text
56c56
< n=17  sigSX=   -5.670742    sigCOH=   -4.500195    sigTOT=  -10.170936    VH=  189.059482+  0.000000i  Eo=   -1.339761
---
> n=17  sigSX=   -5.670742    sigCOH=   -4.500195    sigTOT=  -10.170936    VH=  189.059483+  0.000000i  Eo=   -1.339761
```

Across all 1618 numeric fields in the file the worst deviation is **1.0e-6 absolute /
5.3e-9 relative**. Anything of that size is rounding. A real regression moves `sigSX`,
`sigCOH` or `sigTOT`, and moves them in the third decimal or worse.

## 4. The red banner this run prints is benign

A successful fixture run prints, in red, roughly:

```text
*** LORRAX SANITY FAILURE: H0 = kin_ion + V_H[ISDF] is UNPHYSICAL — 86 of 120 (k,n) have an
implied Vxc outside [-50, 2] eV (worst: k=1 n=29, Vxc=-144.976 eV).  eqp0/eqp1/eqp_g0w0 are
NOT trustworthy.  Sigma may still be fine — the mean-field side is what failed. ***
```

**The run still exits 0 and still reproduces `eqp_ref.dat` to the tolerance above.** The
banner is telling the truth about a real limitation of the *shipped fixture*, not about
your build:

* It is about the **mean-field side** (`H0 = kin_ion + V_H`), not about Σ. The banner says
  so, and the file bears it out — every `sigSX`/`sigCOH`/`sigTOT` column matches the
  reference exactly.
* The cause is that the shipped `kin_ion.h5` does **not** carry an exact $V_H$, so $V_H$
  is supplied by the 60-centroid ISDF quadrature and the ~500 eV cancellation in `H0` does
  not close. The fixture is deliberately tiny; 60 centroids cannot resolve
  $\langle nk|V_H|nk\rangle$.
* Which of `eqp0`/`eqp1` you can trust follows from that: the Σ columns, yes; the
  quasiparticle energies built on top of `H0`, no. For the purpose of "did LORRAX build and
  run correctly", the Σ columns are the answer.

!!! warning "Do not 'fix' the banner before comparing to the reference"
    The banner's own printed remedy — regenerate `kin_ion.h5` with `gw.kin_ion_io` — does
    work: measured 2026-08-06, `lx run python3 -u -m gw.kin_ion_io -i cohsex_test.in`
    produces a 469 KB `kin_ion.h5` (the shipped one is 145 KB) and the banner disappears
    completely. **But the run then no longer reproduces `eqp_ref.dat`**: `VH` changes from
    189.06 to 591.65 at `k=0,n=0`, the column loses its complex formatting, and the diff
    grows to 562 lines. `eqp_ref.dat` was generated *with* the shipped `kin_ion.h5`.
    Regenerate it to get physical `H0`; keep it as shipped to reproduce the reference.
    You cannot do both with this fixture.

The other two banners a clean run prints are also expected:
`[dipole provenance] … carries no provenance stamp` (the shipped `dipole.h5` predates the
guard) and `[gpu_utils] WARNING: bytes_limit=None, falling back to nvidia-smi` (the
allocator the launcher resolves blinds XLA's arena accounting — see the
[startup block](environment/overview.md#startup-block)).

## 5. Run the regression test

The same fixture is wrapped as a pytest regression (it shells out to the driver and is
CPU-capable):

```bash
uv run python -m pytest -q       # the DEFAULT GATE: the Si end-to-end calculation for
                                 # the drivers you touched + the services' suites
uv run python -m pytest -q --census   # the CENSUS: everything (see docs/contributing.md)
lx test                          # on Perlmutter: the default gate, on a compute node, in cwd
lx test --census                 # on Perlmutter: the census
```

## Your first real calculation {#your-first-real-calculation}

You need a `WFN.h5` first — see [Preparing inputs from DFT](preprocessing.md). Given one,
you produce three preprocessing artifacts, then run GW:

1. **Centroids** — `python -m centroid.kmeans_cli <N> --seed 42` → `centroids_frac_<N>.txt`
2. **Dipoles** — `python -m psp.get_dipole_mtxels -i cohsex.in` → `dipole.h5`
3. **Kinetic + ionic** — `python -m gw.kin_ion_io -i cohsex.in` → `kin_ion.h5`
4. **GW** — `python -m gw.gw_jax -i cohsex.in`

On NERSC Perlmutter, `lxpre cohsex.in <N>` bundles steps 1–3; `lx run` is how you launch
any of them ([Perlmutter §1](environment/machines/perlmutter.md#1-entry-point-lx)).

!!! danger "Three of these four steps have defects that bite on a first run"
    All three were reproduced on Perlmutter 2026-08-06 against the bundled fixture. They
    are **code** defects, registered as such; the workarounds below are how you get through
    the chain today, not the fix.

    **Step 1 ignores `wfn_file` and reads `WFN.h5`.** The filename is hardcoded
    (`centroid/kmeans_cli.py:427`, `WfnLoader("WFN.h5")` — the spelling changed with
    the 2026-08-07 service extraction, the defect did not) and there is no CLI flag to
    override it — the parser has no `--wfn`. If your wavefunction is named anything else,
    including the fixture's own `WFNsmall.h5`, you get a naked traceback ending in
    `FileNotFoundError: … name = 'WFN.h5'` from inside h5py, with none of the
    announce-or-refuse framing the rest of the codebase uses. *Workaround:* run it in a
    directory where the file is called `WFN.h5` (`ln -s WFNsmall.h5 WFN.h5`).

    **Step 1's output filename does not carry the `N` you asked for.** The name is built
    from the count that survives grid-snap dedup and pivoted-Cholesky pruning, not from
    your request (`kmeans_cli.py:580`, `f"centroids_frac_{n_unique}…"`). Asking for 60 on
    the fixture writes **`centroids_frac_56.txt`**. Nothing warns you, and step 4 then
    fails to find the `centroids_file` your deck names. *Workaround:* read the
    `Saved centroids to …` line the run prints and set `centroids_file` from it.

    **Step 2's output cannot satisfy the guard step 4 applies to it.** Step 2 stamps
    `dipole.h5` with the band window it read from your deck. Step 4 re-derives that window
    from a dict that does not contain it, so it compares your stamp against hardcoded
    defaults and reports a mismatch whose printed remedy is *the command you just ran*:

    ```text
    *** LORRAX SANITY FAILURE: dipole.h5 was generated from a DIFFERENT DFT solution or band
    window than this run (prov_nval: file=4 run=5; prov_ncond: file=4 run=5; prov_nband:
    file=40 run=150). … Regenerate it with `python -m psp.get_dipole_mtxels -i <deck>`. ***
    ```

    The fixture deck says `nval = 4`, `ncond = 4`, `nband = 40`; `file=` is those values,
    correctly stamped. Following the documented chain therefore *cannot* clear the banner
    for any deck whose window is not `5 / 5 / max(nbands, nelec+5)`. *Workaround:* none
    needed — the guard is reporting on itself, not on your file. The run continues and is
    unaffected unless `LORRAX_SANITY=strict`, which turns it into a refusal.
