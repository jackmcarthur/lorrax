# 12.2 Memory planning

Set `memory_per_device_gb` to the usable VRAM (device memory minus ~2 GB
headroom); the planner sizes every chunked loop from it. The ζ fit and $V_q$ build
are streamed over band chunks (the FFT stage), grid chunks (the fit's right-hand
sides), q batches, and G chunks, and the planner chooses each size against an
analytic per-stage high-water-mark model with four named peaks: the band-chunked
centroid load, the fitting-matrix build + factorization, the pair-density
workspace of the fit kernel (usually the binding peak, and ~3× more demanding per
band in bispinor runs), and the ζ accumulation. The model is faithful to measured
peaks within ~15%.

The planner prints its decisions (chunk sizes, per-peak predictions) at startup;
read that block before anything else when a run OOMs. Overrides exist for every
chunk size (`band_chunk_size`, `r_chunk_override`, `gflat_chunk_size`,
`vq_g_chunk_size`; 0 = auto) but the planner beats manual choices in practice, and
the supported fix for a genuine OOM is more devices, since every large axis is
sharded and per-device footprint falls with pool size (§4.3). Memory grows
linearly with $N_k$ and quadratically with $n_\mu$; the planner arithmetic makes
the minimum pool for a target system explicit before any compute is spent.
