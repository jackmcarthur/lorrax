# 1.3 Relation to Quantum ESPRESSO and BerkeleyGW

Quantum ESPRESSO is the DFT starting point: SCF density, NSCF wavefunctions on the
GW k-grid, exported with `pw2bgw.x`. Fully-relativistic ONCV pseudopotentials are
the standard choice — the code is spinor-first (§5.2).

BerkeleyGW supplies the file formats and conventions: `WFN.h5` layout, symmetry
conventions, Coulomb-divergence handling, `eqp.dat`-style output. Where the
formalisms coincide (static COHSEX; plasmon-pole GW at matched parameters) the two
codes agree at the meV level, and the test suite pins several of these comparisons
permanently. Appendix E is the matched-comparison recipe.

## Pros and cons vs. legacy BerkeleyGW

Pros:

- Runtime $O(N_k \log N_k)$ in k-points (§4.3); the plane-wave pipeline pays
  $O(N_k^2)$. The advantage grows with grid density — dense-k 2D systems are the
  sweet spot.
- $O(N^3)$ in system size vs. $O(N^4)$.
- $\Sigma(\omega)$ directly on the real axis, on a dense user-chosen grid, no
  analytic continuation.
- Bispinor GW: the Breit/current–current channel (Ch. 8).
- Screening cutoffs up to 4× the wavefunction cutoff (§6.3); BGW capped at 1×.
- GPU-native; one code path from laptop to multi-node cluster.

Cons:

- Larger minimum memory workspace: the sharded ISDF problem must fit across the
  device pool at once, so a given system generally needs more processors just to
  start.
- Memory linear in $N_k$ (R-space storage, §4.3); BGW's one-q-at-a-time pipeline
  holds no such state. Deliberate trade — memory is the poolable resource on GPU
  clusters, and it buys the $N_k \log N_k$ runtime.
- Spinor wavefunctions only. No spinless or collinear-spin mode; silicon runs at
  spinor cost.
- DFT input from Quantum ESPRESSO only, via the BGW format.
- Younger validation record.

Rule of thumb: dense k-grids, GPU allocations, SOC-heavy or magnetic systems, full
$\Sigma(\omega)$ → LORRAX. Minimal hardware, spinless or collinear systems, other
DFT starting points → legacy BerkeleyGW.
