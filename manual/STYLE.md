# Style conventions for manual writing

Reference prose: the first four paragraphs of the repo `README.md`. Read them before
writing; match them. The register is a grad student giving a talk they had to cut
hard to fit the time limit — dense declaratives, every sentence carrying new
technical content, costs stated in the same breath as features, limitations blunt,
novelty said once with "novel" and then dropped.

What kills that register (don't do these):

- Tagline bullets and bolded concept names ("**Front-end breadth.** ...").
  Bold is for file paths and input keys, not rhetoric.
- Marketing or clever headers. "Pros of LORRAX", not "Where LORRAX wins".
- Meta-commentary, previews, recaps, drama ("this section explains", "the friendly
  case", "a fair summary for the impatient"). The content stands alone.
- Complete-sentence bias in lists and tables — fragments are correct there.
- Arguing uniqueness. State the property and its consequence; the "first code to
  combine these scaling breakthroughs" framing appears once, in 1.1.

House facts: full name is "the LOw-scaling Real-space Real-Axis eXcited state
package in BerkeleyGW"; QE is the "DFT starting point" (never "front end"); no code
other than QE and BerkeleyGW is named — refer to "the majority of O(N³)-scaling GW
codes" and similar. Forward references are bare parentheticals "(§5.4)". Short
enumerations go inline — "1.) ..., and 2.) ..." — not in bullet cascades.

When in doubt: cut the sentence in half and drop the label.
