# 2.3 The cluster tier: parallel I/O and distributed linear algebra

For multi-node production runs, build the native stack. The pure-Python fallbacks are
*correct* at any scale, but two of them degrade from conveniences into bottlenecks
once a calculation spans nodes — treat this section as part of the cluster install,
not as tuning.

## The three libraries

**1. Parallel HDF5 (MPI-IO).** Engaged by `slab_io` (auto-selected when available).
Every rank writes its own shard of ζ, Σ(ω), and restart data concurrently; without
it, terabyte-class ζ stores funnel through rank 0. Obtain via conda-forge
(`hdf5=*=mpi_*`) or spack (`hdf5+mpi`) on generic clusters, or the Cray
`cray-hdf5-parallel` module plus the provided stage script on Cray systems. The CMake
build *enforces* `HDF5_IS_PARALLEL` — a serial HDF5 is rejected with a clear error
rather than silently linked.

**2. cuSOLVERMp + CAL (and cuBLASMp).** Distributed Cholesky/LU/eigh and the fused
W-solve on NVIDIA GPUs; engaged by `distributed_cholesky` / `distributed_lu` /
`screening_solver` (all default `auto`). Easiest acquisition is the PyPI wheel:

```bash
pip install nvidia-cusolvermp-cu12==0.7.2.888 nvidia-cal-cu12
```

**Version pin matters:** cuSOLVERMp 0.6.0 silently returns *wrong answers* on
process meshes with both dimensions > 1; 0.7.2 contains the fix. The build accepts
`-DCUSOLVERMP_INCLUDE_DIR/-DCUSOLVERMP_LIB_DIR` pointed at the wheel, an NVHPC SDK,
or a spack install.

**3. SLATE (+ blaspp/lapackpp).** The portable alternative for the same dense
operations — including on CPU nodes — selected per-operation from the input file
(`distributed_cholesky = slate`). Built from source via the provided scripts; the
superbuild lands blaspp/lapackpp under the same prefix.

## Building the FFI layer

```bash
bash src/ffi/common/cpp/build.sh      # produces liblorrax_ffi.so
```

with `-D` overrides for any library prefix that isn't auto-detected. The build is
per-machine, takes minutes, and is validated by a skipif-gated contract test suite
(`tests/test_ffi_linalg_contract.py`) that exercises every backend × mesh × dtype
combination it can find — run it once after building.

## Semantics worth knowing

- **`auto` means "best available, loudly."** Backend keys default to `auto`: use the
  native path when the library is present, fall back to the pure path when it is
  genuinely absent — but a key set *explicitly* (`distributed_cholesky = slate`) that
  cannot be honored is a hard error naming what is missing and how to build it. No
  silent downgrades.
- **Library limits are guarded.** Known failure geometries of the vendor libraries
  (non-square meshes for certain operations, rank-divergent parameter combinations)
  are rejected with explanatory errors instead of hangs; §12.3 lists them.
- **MPI is the launcher's business.** The FFI layer piggybacks on the same
  one-process-per-GPU launch the pure tier uses (§12.1); there is no separate MPI
  world to configure beyond what your `srun`/`mpirun` already provides.
