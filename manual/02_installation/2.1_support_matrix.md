# 2.1 JAX and the structure of the installation

LORRAX is written entirely in Python on top of JAX, an array-computing library in
which NumPy-style code (`jnp.einsum`, `jnp.fft`, ...) is traced and just-in-time
compiled by the XLA compiler into fused kernels for whatever hardware is present,
so one source runs at native speed on NVIDIA GPUs or CPU cores with no hand-written
CUDA in the physics code. The property that matters most for LORRAX is JAX's
multi-device execution model: arrays are declared as sharded across a mesh of
devices spanning many processes and nodes, the compiler inserts the required
communication, and the entire GW pipeline is expressed as single-program
multiple-data array arithmetic, one Python process per GPU (Ch. 13).

Installation is therefore mostly ordinary Python packaging. `uv sync` installs
LORRAX editable together with JAX ≥ 0.9 and its CUDA-13 wheels (the wheels bundle
the CUDA runtime, so no system CUDA installation is needed), and this bare-venv
route is a complete install for CPU work, single nodes, and development (§2.2).
Where a site stack makes user Python environments impractical, the same source runs
inside a container: on Perlmutter LORRAX runs in the NVIDIA JAX image under
Shifter with the source tree and native libraries bind-mounted (§2.4), and
Apptainer plays the same role on other clusters. Neither route changes any input or
output.

Two things JAX does not provide, and they define the rest of this chapter. First,
its cross-process collectives cover array arithmetic (sums, permutations,
transposes) but not dense linear algebra: there is no distributed Cholesky, LU, or
eigendecomposition, and factorizing a matrix sharded across processes means
gathering it to one device. LORRAX ships a hand-blocked pure-JAX Cholesky that
covers moderate problem sizes, but the large-$n_\mu$ factorizations, solves, and
eigenproblems of production runs call vendor libraries (cuSOLVERMp, cuBLASMp,
SLATE) instead. Second, JAX performs no parallel file I/O, so the multi-GB ζ and
Σ(ω) datasets would otherwise funnel through serial HDF5 on one rank; MPI-IO
parallel HDF5 removes this. Both capabilities enter through one native library,
`liblorrax_ffi.so`, built once per machine (§2.3) and selected from the input file
(`distributed_cholesky`, `distributed_lu`, `screening_solver`, `slab_io`, all
defaulting to `auto`). A fresh clone contains no `liblorrax_ffi.so`; pure-JAX paths
never touch it, and an explicitly requested backend that is missing fails loudly
with the build command rather than falling back silently.
